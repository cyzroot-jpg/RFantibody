# 排错手册（实战记录）

按“现象 → 原因 → 处理”组织，均来自真机调试。

## A. 环境 / 启动

| 现象 | 原因 | 处理 |
|------|------|------|
| `AssertionError: local_world_size (4) must be less than or equal to the number of visible devices (1)` | 未暴露 4 个核组 | `export SDAA_VISIBLE_DEVICES=0,1,2,3`（单卡 TP=4） |
| 4 个 Worker 100% CPU 卡在 `tcclBarrierNode/tcclSocketWait` | `torch_sdaa` 与 SDAA Runtime/TCCL 版本不匹配（运行时被升级） | 回退到 3.2.0（见执行手册阶段 0）；`tecolmk` 保持 3.3.0 |
| `vllm_sdaa._C.so: undefined symbol: tecolmkFusedRecurrentGatedDeltaRuleV2` | `tecolmk` 被降到 3.2.0 | 还原 `tecolmk 3.3.0`（`/var/teco-repo/tecotoolkit/`） |
| `RuntimeError: SDAA error: invalid argument`（在 `torch.einsum`） | 新运行时下 sdaa einsum 异常 | RoPE 的 cos/sin cache 改在 **CPU** 构建后再 `.to(sdaa)` |
| RPM 安装报 `needs XXX more space` | `/` 磁盘满 | 清理 `/tmp`、`~/.cache` 等 |
| `vllm serve` 启动即 `bash: <path>: No such file or directory` | `run_ci.py` 传相对路径给 `bash`，且 `cwd` 是 run.sh 的父目录 | `run_ci.py` 传 **绝对路径** run.sh |
| `SDAA_VISIBLE_DEVICES` 设为 `0` 却想 TP=4 | 只暴露 1 个核组 | 设 `0,1,2,3` |

## B. 配置 / Tokenizer

| 现象 | 原因 | 处理 |
|------|------|------|
| `ValueError: ... model type 'xxx' but Transformers does not recognize` | transformers 无该 config | 自定义 `PretrainedConfig` + `AutoConfig.register(model_type, ...)`；如嵌套 `text_config`，转成子 config 实例 |
| `KeyError: model_type`（vLLM convertor） | `MODEL_ARCH_CONFIG_CONVERTORS` 不含该 model_type | `MODEL_ARCH_CONFIG_CONVERTORS.setdefault(mt, 最接近的Convertor)` |
| `AttributeError: 'list' object has no attribute 'keys'`（tokenizer 初始化） | `tokenizer_config.json` 的 `extra_special_tokens` 是 transformers 5.x 的 **list** 格式 | 改成 dict（`{"extra_0": "<|...|>"}`），或提供改好的模型目录 |
| tokenizer 加载失败影响 evalscope perf | perf 会从 `<vllm serve 的路径>` 加载 tokenizer | 让 `vllm serve` 指向“软链原始权重 + 覆盖 tokenizer_config.json”的目录 |

## C. 组网 / 权重

| 现象 | 原因 | 处理 |
|------|------|------|
| 输出乱码/重复但能跑 | 权重没加载对 / k_eq_v 未复制 / 前缀没剥离 | 对照 checkpoint 权重名核对 `load_weights`；`k_eq_v` 层用 k_proj 复制 v_proj；剥离 `language_model.` 等前缀 |
| 精度接近随机 | 用了 vLLM 原生 Norm/RoPE（没接 tecoops）或 norm 语义错 | 统一用 `tecovllm_models.layers`；注意 Gemma RMSNorm 是 `x*w`（旧 Gemma 家族是 `x*(1+w)`），以 HF/vLLM 当前实现为准 |
| `--dtype float16` 与 config bf16 不一致告警 | checkpoint 是 bf16，SDAA 用 fp16 | 显式 `--dtype float16` |
| KV cache 报 `need X GiB, larger than available` | `max_model_len` 太大 / 显存被占 | 调小 `--max_model_len`（如 32768）；调大 `gpu_memory_utilization`；关掉占卡进程 |

## D. 算子 / 精度定位

| 现象 | 原因 | 处理 |
|------|------|------|
| 自定义 FA 路径输出乱码，`TECO_BASIC_FA=1`（纯 torch）正常 | tecoops FA 路径的问题（布局/kernel） | 先查 KV 布局是否 HND、block_size 是否 32、`window_size`/`softmax_scale` 是否透传 |
| `head_dim>128` 时 FA 结果全错/NaN（hd 128 正常） | SPM(~256KB/SPE) 溢出 | kernel 按 head_dim 缩 BM：>128→64，>256→32 |
| 自定义 scale（如 `scaling=1.0`）结果错 | kernel 默认 `1/sqrt(d)` | 把 `softmax_scale` 透传到 `args.softmax_scale` |
| sliding 结果错 | window 语义/掩码方向错 | 语义为“含当前 token 的窗口大小 w”，allowed `[rel-w+1, rel]`；在 `apply_causal_mask` 内融合 |
| reshape_and_cache 结果可疑 | 非连续输入 / 布局 | key/value `.contiguous()`；cache 用 HND |

## E. 评测 / 性能

| 现象 | 原因 | 处理 |
|------|------|------|
| 精度评测极慢（每条数分钟） | 未优化 kernel + mmlu_pro 5-shot 要求逐步推理（输出长） | 属 baseline；非思考模式也一样（`enable_thinking:false` 不含 thinking 标记） |
| 评测结果 0.0x（异常低） | `max_tokens` 太小被截断，没输出 `ANSWER:` | 用 spec 的 `max_tokens=1024` |
| CI `prec.sh` 与本 SKILL 第 4 节 `enable_thinking` 不一致 | 仓库 CI 对 gemma 用 `true`，任务书用 `false` | 本地按任务书跑；注意 `tools/ci_pipline/` 不可修改，本地临时改完要还原 |
| 性能 T4 失败：`RPC call to sample_tokens timed out` | 单次执行超过 `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS`(默认 300s) | run.sh 加 `export VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS=3600` |
| `results` 提取报 `存在 N 条失败请求` | 上一条超时导致 EngineCore 挂 | 先修超时，再重跑性能 |

## F. 通用调试技巧

- 用 `TECO_BASIC_FA/RAC/RMS=1` 在纯 torch 参考路径与 tecoops 路径之间 A/B，快速判断是模型问题还是算子问题。
- 模型输出不对时，先用**单条 chat** 看是否连贯，再跑精度；连贯性差几乎一定是权重/kernel 问题。
- 单算子问题先在 `python_api_test` 里用“随机输入 + CPU float32 参考”定位（注意 elapsed 对齐/同步）。
- `run.sh` 与 `run_ci.py`：run.sh 里 `vllm serve` 用**绝对路径**，且 `--port` 显式指定。
